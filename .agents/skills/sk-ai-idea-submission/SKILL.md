# SK AI Idea 사례 출품 준비

처음 보는 평가자가 문제, 구현, 성과를 한 번에 이해하고 각 주장까지 검증할 수 있는 출품 초안을 만든다. 공개 저장소에는 공개 가능한 일반 지침과 공개 근거만 남기고, 내부 공지 전문·경쟁작 화면·사내 수치·개인정보는 복제하지 않는다.

## 시작할 때

1. 현재 요청에 제공된 공식 양식과 규정을 우선 읽는다. 저장소의 요약본보다 최신 공지가 우선이다.
2. 작품별 작업 폴더를 `submissions/<repo-slug>/`에 만들고 [case-intake-template.md](assets/case-intake-template.md)를 `facts.md`로, [submission-template.md](assets/submission-template.md)를 `draft.md`로 복사한다.
3. 저장소와 실제 배포 사이트를 모두 확인한다. README만으로 동작을 단정하지 말고, 화면에서 핵심 흐름과 오류 상태를 검증한다.
4. [rubric-and-rules.md](references/rubric-and-rules.md)와 [writing-playbook.md](references/writing-playbook.md)를 읽는다. 수치·보안·저작권 판단이 필요한 경우 [evidence-and-security.md](references/evidence-and-security.md)도 읽는다.

처음에는 저장소·배포 URL, 해당 연도 실제 활용 여부, 대상 사용자와 기존 흐름, AI·코드·사람 승인 흐름, 정량 근거 보유 여부만 확인한다. 저장소·사이트 점검 뒤 남은 질문을 중요도순 3~5개씩 나눈다. URL 누락, 접근 제한, 배포 오류는 사유와 확인 시각을 근거 원장에 기록하고 코드나 동작을 추측하지 않는다.

## 근거 원장부터 만든다

각 주장을 다음 네 상태 중 하나로 표시한다.

- `검증됨`: 공개 코드, 배포 화면, 테스트 결과, 승인된 업무 기록으로 확인됨
- `사용자 확인`: 실제 시간 절감, 사용 빈도, 이용자 수, 의사결정 효과처럼 제작자만 확인할 수 있음
- `추론`: 정황상 가능하지만 출품문에 사실로 쓰면 안 됨
- `제외`: 기밀, 개인정보, 고객 데이터, 비공개 원자료, 로그, 경쟁작 상세, 재배포 권리가 불명확한 자료

운영 빈도·담당자 같은 사실은 사용자 진술임을 표시해 사용할 수 있다. 시간·비용·생산성 같은 정량 Impact는 사용자 확인만으로 확정하지 않고, 기존값·현재값·기간·표본·측정법·근거·공개 승인을 갖춘 경우에만 단정한다. 나머지는 `[확인 필요: ...]` 또는 `[검증 대기: ...]`로 남긴다. 측정하지 않은 성과를 계산해 사실처럼 만들거나, 좋아요 수를 품질의 증거로 사용하지 않는다.

## 작품 후보 비교

후보가 여러 개이면 같은 증거 수준에서 다음 세 축을 각각 1~5점으로 비교한다.

- Biz Impact: 반복 업무의 제거, 의사결정 품질, 리스크 감소, 시간·비용·생산성의 증거
- 확장 가능성: 입력·규칙·출력의 표준화, 다른 조직이 재현하는 데 필요한 전제와 운영 난이도
- 혁신성: 단순 요약을 넘어선 새로운 문제 정의, 검증 가능한 AI-코드 협업, 감사 추적, 사람의 판단을 강화하는 구조

공식 세부 가중치가 제시되지 않았다면 임의 가중 합계를 공식 점수처럼 표현하지 않는다. 대신 강점, 증거 공백, 보안·저작권 리스크를 함께 제시하고 2~3개를 추천한다.

## 초안 작성 순서

초안을 쓰기 전에 한 줄씩 이어지는 이야기 뼈대를 먼저 만든다: `왜 중요한 업무인가 → 사람이 할 때 무엇이 어려운가 → AI와 프로그램이 무엇을 바꿨는가 → 어떤 가치가 생겼는가 → 다른 조직이 왜 재사용할 수 있는가`. 공식 양식의 제목은 유지하되, 독자가 항목별 답변의 모음이 아니라 하나의 사례로 읽게 한다.

1. **사례명과 개요**: 대상 사용자, 고통, 변화를 한 문장에 담고 검증된 대표 수치가 있을 때만 포함한다. 수치가 없으면 억지로 만들지 않는다. 기능 이름만 나열하지 않는다.
2. **Why**: 현업 의사결정과 연결된 As-Is 흐름, 빈도, 병목, 오류·누락 위험, 해결하지 않을 때의 비용을 쓴다.
3. **How / What**: 독자가 해결 방법과 신뢰 장치를 이해하는 데 필요한 만큼만 쓴다. AI 도구별 역할, 사람의 승인 지점, 데이터 흐름, 규칙·코드·테스트·배포 구조, 실제 프롬프트 예시를 설명하되 기술 과정이 현업 이야기를 밀어내지 않게 한다. 업무의 복잡성을 만드는 대상·기간·가중치·산식이 핵심이라면 실제 구성을 밝히고 3~5단계의 쉬운 말로 풀어 쓴다. 비밀값과 내부 데이터는 마스킹한다.
4. **Biz Impact**: `기존값 → 현재값`, 측정 기간, 표본, 산식, 근거 위치를 함께 쓴다. 결과 수치가 없으면 먼저 측정 계획을 제시하고 초안에는 확인표시를 둔다.
5. **확장 가능성**: 바꿔야 하는 입력·규칙·용어와 그대로 재사용되는 작업 흐름을 분리한다. 도입 전제, 1회성 설정, 일상 운영, 실패 시 대응을 적는다.
6. **혁신성**: AI 사용 자체가 아니라 기존 방식과 다른 의사결정 구조를 설명한다. 예: 원문과 정리된 데이터 분리, AI 판단과 규칙에 따른 계산 분리, 별도 자료를 이용한 재확인, 결과에서 원자료까지 다시 확인할 수 있는 기록.
7. **제출 패키지**: 본문과 함께 대표 이미지 1장, 문제-과정-성과 이미지, 시스템 구조도, 데모 링크, 공개 가능한 GitHub 링크, 출처·라이선스 표를 제안한다.

## 차별화 원칙

- 평가자가 첫 화면에서 이해할 수 있는 쉬운 제목을 먼저 보여준다. 검증된 대표 수치가 있으면 숫자 1개를 함께 쓴다.
- 본문에서는 숫자의 출처와 재현 경로를 보여 전문가 검증에 견디게 한다.
- “AI가 만들었다”보다 “사람의 판단이 어디서 빨라지고 안전해졌는가”를 중심에 둔다.
- 약어는 처음 나올 때 전체 이름을 먼저 쓰고, 사내·개발 용어는 처음 보는 사람도 이해할 수 있는 일상어로 바꾼다. 기술 용어가 꼭 필요하면 같은 문장에서 뜻을 설명한다.
- 문장을 모두 같은 길이와 어미로 맞추지 않는다. 과장된 수식어, 억지로 만든 세 가지 묶음, 반복되는 “~했습니다”, 내용 없는 연결어와 홍보 문구를 걷어낸다.
- 제작자의 실제 관찰, 판단 이유, 아직 모르는 부분은 남긴다. 자연스러워 보이게 하려고 경험·수치·감정을 새로 만들지 않는다.
- 실제 오류 이력이 없으면 “오류가 많았다”고 쓰지 않는다. 데이터와 계산 단계가 많아 오류가 발생하기 쉬운 구조와 확인된 실제 오류·재작업 성과를 구분한다.
- “누구나 평가할 수 있다”처럼 권한까지 개방한 것으로 읽히는 표현은 피한다. 같은 자료와 규칙을 공유받은 검토자가 계산을 재현할 수 있다는 투명성과 공식 평가 권한을 구분한다.
- 경쟁작의 문구·레이아웃·기능을 복제하지 않는다. 관찰한 것은 일반적인 전달 원칙으로만 추상화한다.
- 불확실성, 데이터 한계, 사람이 승인하는 지점을 숨기지 않는다. 통제 장치가 있는 정직한 한계는 신뢰 근거다.

## 완료 조건

- 모든 정량 주장에 기준값, 현재값, 측정 범위, 근거가 있다.
- 사용한 AI 도구와 실제 역할이 확인됐고 일반/A.biz 구분을 사용자가 확정했다.
- 처음 보는 사람이 30초 안에 문제-해결-성과를 요약할 수 있다.
- 약어와 기술 용어를 모르는 독자도 별도 검색 없이 읽을 수 있고, 공식 양식 안에서 한 이야기로 이어진다.
- 최종 문체 점검에서 상투적인 AI 문장 패턴을 줄였으며 원래 주장과 사실은 바뀌지 않았다.
- 다른 조직의 도입 전제와 재사용 범위가 구체적이다.
- 비식별, 공개 가능성, 오픈소스 라이선스, 외부 자료 재배포 권리를 점검했다.
- 배포 사이트의 핵심 흐름과 제출용 스크린샷에 오류·민감정보가 없다.
